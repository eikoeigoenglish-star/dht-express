# DHT EXPRESS — 広域3Dステージ（プロトタイプ）

北緯 **37°40′23″（37.6731°N）以南** の日本（本州南部・四国・九州・南西諸島〜沖縄・先島）を、
Three.js 上の 1 つの連続した 3D 空間として表示し、**俯瞰（MAP VIEW）** と **一人称の自由飛行（EXPLORE VIEW）** で探索できる Web アプリです。

将来「DHT EXPRESS」の列車と 9 体のキャラクターを載せるための**ステージ（土台）**であり、今回は列車・キャラクター・ルート線・カウンター等は一切含みません。

> **v2 追加（都市・新幹線駅・ランドマーク）**
> 既存の地形・操作・座標系・LOD・カメラ・GitHub Pages 対応はそのままに、次の 3 つを増築しました（詳細は [§11](#11-都市新幹線駅ランドマークv2-追加)）。
> - 人口10万人以上の **240 都市**の簡略都市メッシュ（InstancedMesh・距離 LOD・地形の市街地色）
> - 東京〜鹿児島中央の **新幹線全 46 駅**（マーカー・駅名ラベル・`route.js` と接続できる駅データ）
> - **17 件のランドマーク**（基本形状で作ったオリジナルの簡略モデル。橋 3 件は海峡を跨ぐ構造物）

> **v3 追加（飛空艇操作・湖沼・河川）**
> v2 の地形・都市・駅・ランドマーク・MAP VIEW・LOD・座標系・GitHub Pages 対応はそのままに、次の 2 つを改修しました（詳細は [§12](#12-飛空艇操作湖沼河川v3-追加)）。
> - **EXPLORE VIEW を「飛空艇」操作に**（FF6 の飛空艇・聖剣伝説のフラミーのイメージ）：前進・旋回・上昇下降だけで飛ぶ。固定速度 30,000 km/h（Shift 90,000 km/h）、最低高度 1,000m、マウス視点は上下左右とも反転
> - **湖沼 20（富士五湖は 5 湖別々）と河川 26 本の本流**を、地形に彫り込んだ水面として追加（水面メッシュ 2 つ＝ draw call +2、都市メッシュに水域マスク、距離で出し分けるラベル）

> **v4 改修（実測 DEM による地形標高）**
> 都市・駅・ランドマーク・湖沼・河川・飛空艇操作・MAP VIEW・LOD 構造・座標系・GitHub Pages 対応はそのままに、**陸地の標高を手続き生成から実測 DEM（Copernicus DEM GLO-90）ベースへ置き換えました**（詳細は [§13](#13-実測-dem-による地形v4)）。
> - **御坂山地が甲府盆地と富士五湖を隔てる**、房総丘陵・三浦丘陵・丹沢・箱根・伊豆・鈴鹿・六甲・紀伊・中国・四国・九州山地などの地域地形が実データで再現されます（垂直倍率は従来どおり 3 倍のまま）
> - 細い尾根を消さない「尾根保存ブレンド」で 1km / 4km 格子へ縮約。配信データ量・ファイル数・LOD・draw call は v3 と同じ（生 DEM は配信しない）
> - 湖面標高を DEM から再計算（内陸の湖は湖岸線も DEM の水面から再作成）、河川は流路を DEM の谷筋へ補正し、川のための地形の掘り込みを大幅に縮小
> - 地形確認用カメラプリセット 4 件を追加（甲府・御坂・富士五湖／房総半島南部／三浦半島／丹沢・箱根）

## 1. 起動方法

ビルド不要・サーバー処理不要の**純粋な静的サイト**です。

### GitHub Pages で公開する

1. このフォルダの中身をリポジトリのルート（または `docs/`）に置いて push
2. GitHub の **Settings → Pages** で、公開するブランチとフォルダ（`/ (root)` または `/docs`）を選択
3. `https://<ユーザー名>.github.io/<リポジトリ名>/` を開く

- すべて **相対パス**（`./js/...`, `./data/...`）で参照しているので、リポジトリ名付きのプロジェクトサイトでもそのまま動きます。
- Three.js はリポジトリ内に同梱しているため、CDN や外部 API への依存はありません。
- `.nojekyll` を同梱しています（Jekyll 処理をスキップして即公開されます）。

### ローカルで確認する（開発用）

`file://` で直接開くと、ブラウザの制約で ES Modules とデータの読み込みができません。簡易 HTTP サーバー経由で開いてください。

```bash
cd dht-express-stage
python3 -m http.server 8000
# → http://localhost:8000/ をブラウザで開く
```

Node.js がある場合は `npx serve .` などでも構いません。**これは確認用であり、公開時にサーバー処理は不要**です。

推奨ブラウザ：最新の Chrome / Edge / Firefox / Safari（WebGL2 と Import Maps に対応したもの）。

## 5. 緯度経度 → 3D 座標の変換ルール

`js/geo.js` にすべて集約しています（`tools/build_terrain.py` と同じ定数）。

### 座標軸

| 軸 | 意味 |
|---|---|
| **+X** | 東（-X が西） |
| **-Z** | 北（+Z が南）＝ Three.js でカメラの「奥」が北 |
| **+Y** | 上（標高）。**海面 = Y 0** |

### スケール

- **水平：1 world unit = 1 km（実距離そのまま）**
- **垂直：Y = 標高[m] ÷ 1000 × 3**（`VERTICAL_EXAGGERATION = 3`、山を見やすく 3 倍誇張）

### 投影法：正弦図法（中央経線 132.5°E、基準緯度 31.0°N）

```js
x =  (lon - 132.5) * KM_PER_DEG * cos(lat)
z = -(lat - 31.0)  * KM_PER_DEG          // KM_PER_DEG = 111.195 km
```

- 南北方向の距離と、各緯線に沿った東西距離が正確。逆変換も厳密。
- 例：東京駅 → `(656.4, -520.5)`、鹿児島中央駅 → `(-185.6, -64.9)`。
  ワールド上の直線距離 957km、大圏距離 967km（誤差 1% 程度）。

### API

```js
import { latLonToWorld, worldToLatLon, metersToY, haversineKm } from './js/geo.js';

const { x, z } = latLonToWorld(35.681, 139.767);    // 東京駅
const { lat, lon } = worldToLatLon(x, z);           // 逆変換
const y = DHT.terrain.getSurfaceY(x, z);            // その地点の地表 or 海面の Y
haversineKm(35.681, 139.767, 31.584, 130.541);      // 実距離 [km]
```

### 実距離・ルート上の位置との関係（将来）

```
緯度経度 ──latLonToWorld()──▶ ワールド (x, z)    [1 unit = 1 km]
     │
     └─haversineKm()──▶ 区間 km ──累積──▶ ルート上の位置 (km)
                                            ▲
         progressKm = totalCount（DHT 1回 = 1km）
```

`js/route.js` の `GeoPolyline` は、ルートの緯度経度列を受け取り、
`getPointAtKm(progressKm)` で「緯度経度・ワールド座標・進行方向」を返します。
営業キロ（東京〜鹿児島中央 1395km）と折れ線実測長の差は `totalKm` オプションで正規化します。
**今回はルートデータを定義しておらず、画面にも何も描画しません。**

## 6. 操作方法

### 共通

| キー | 動作 |
|---|---|
| `1` | 俯瞰モード（MAP VIEW） |
| `2` | 一人称探索モード（EXPLORE VIEW） |
| `L` | 地名ラベル表示 ON/OFF（都市・駅・ランドマークのラベルも含む） |
| `B` | 都市メッシュ（建物）表示 ON/OFF（v2。性能比較用。市街地の地表色は残る） |
| `I` | 情報表示（FPS / draw call / 三角形数 / 位置 / 高度）ON/OFF |
| `H` | 操作説明の表示／折りたたみ |

画面左上のボタンでもモードを切り替えられ、現在のモードは黄色で表示されます。

### 俯瞰モード（MAP VIEW）

| 操作 | 動作 |
|---|---|
| 左ドラッグ | 回転 |
| 右ドラッグ（または Shift + 左ドラッグ） | パン（地面に沿って移動） |
| ホイール | ズーム（カーソル位置に向かって寄る） |
| 中ドラッグ | ズーム |
| 矢印キー | パン |

- OrbitControls ベース。慣性（ダンピング）あり。
- 見下ろし角は最大 80° に制限（真横にならず酔いにくい）。
- 毎フレーム、カメラが地表・海面に潜らないよう、注視点が地表付近にあるよう補正。
- ズーム範囲：約 1.2km 〜 3400km（日本全体から地表すれすれまで連続的に寄れる）。

### 一人称探索モード（EXPLORE VIEW）— v3「飛空艇」操作

| 操作 | 動作 |
|---|---|
| `W` / `↑` | 前進（機首方位へ**水平に**飛ぶ。視線を下げても地面へ突っ込まない） |
| `S` / `↓` | 後退 |
| `A` / `←` | 左旋回（Yaw。横移動はしない） |
| `D` / `→` | 右旋回（Yaw。横移動はしない） |
| `Q` | 下降 |
| `E`（`Space` でも可） | 上昇 |
| `Shift` | 高速飛行（水平 90,000 km/h・垂直 30,000 km/h） |
| 画面クリック | マウス視点 ON（ポインタロック） |
| マウス移動 | 見回し。**上下左右とも反転**（右へ動かす → 左を見る、下へ動かす → 上を見る） |
| `Esc` | マウス視点の解除 |

- 速度は固定：水平 **30,000 km/h**（Shift 中 **90,000 km/h**）、上昇・下降 **10,000 km/h**（Shift 中 **30,000 km/h**）。ホイールでは変わりません。
- 慣性なし：押せばすぐ動き、離せばすぐ止まります（旋回だけ約 0.07 秒のなめらかさ）。
- **最低高度 1,000m**：周囲 0.8km で最も高い地表から 1.0 km より下には降りられません。山に向かって飛ぶと先読みで前もって上昇し、富士山などの内部には入りません。
- 俯瞰モードから切り替えると、注視点の手前の空中（地表から約 3km）へ滑らかに降下します。一人称から俯瞰へ戻すと、視線が地面に当たる地点を中心にした俯瞰に切り替わります（v2 と同じ）。
- 詳細・定数は [§12.1](#121-explore-view飛空艇操作)。

## 9. パフォーマンス上の注意

### 現状の負荷（目安）

| 状況 | draw call | 三角形 |
|---|---|---|
| 全体俯瞰 | 約 86 | 約 19 万 |
| 地域プリセット（詳細タイル表示中） | 約 25〜65 | 約 6〜22 万 |

v2（都市・駅・ランドマーク追加後）の実測値は [§11.9](#119-パフォーマンス) を参照。

- マテリアルは地形 1 + 海 1 + 海底 1 + 空 1 のみ。テクスチャは波の法線マップ 1 枚（128px）だけ。
- 影（shadow map）は未使用。
- 地形は **128km 四方の粗タイル（4km 間隔）** と **64km 四方の詳細タイル（1km 間隔）** の 2 段 LOD。
  カメラから 170km 以内の粗タイルを詳細タイル 4 枚に分割し、215km より離れたら戻します（ヒステリシス付き）。
- 詳細データは近づいた所だけ fetch（同時 6 本まで）。生成済みメッシュは最大 160 枚までキャッシュし、溢れたら古い順に破棄。
- タイルごとに frustum culling が効きます。地名ラベルは HTML なので draw call を使いません。

### GLB を追加するときの目安

- 地形は最大でも 20 万三角形・数十 draw call 程度なので、
  **列車 1 + キャラクター 9 体（各 1〜3 万三角形・数 draw call 程度）を足しても余裕があります。**
- キャラクターのテクスチャは 1024px 程度・KTX2 圧縮、ジオメトリは Draco / meshopt 圧縮を推奨。
- 影を付ける場合は、地形全体ではなく列車周辺だけを照らす小さな影カメラにしてください。

### その他

- 深度精度のため `logarithmicDepthBuffer` を有効にしています（地表 10m 〜 地平線数千 km を 1 カメラで扱うため）。
  カスタム ShaderMaterial を追加する際は `#include <logdepthbuf_*>` チャンクを入れてください。
- ピクセル比は最大 1.75 に制限しています（高 DPI 画面での負荷対策、`main.js`）。

## 10. 地形データの再生成（任意）

公開には不要です。パラメータ（山の位置・標高、北限の帯など）を変えたいときだけ実行します。

```bash
pip install numpy scipy pillow tifffile imagecodecs scikit-image
mkdir -p ../src_data && cd ../src_data
B=https://raw.githubusercontent.com/nvkelso/natural-earth-vector/master/geojson
for f in ne_10m_land ne_10m_minor_islands ne_10m_lakes ne_10m_rivers_lake_centerlines; do curl -LO $B/$f.geojson; done
cd ../dht-express-stage
python3 tools/dem/copernicus.py --src ../src_data                 # v4: 実測 DEM の取得（初回のみ・88 タイル 約 150MB）
python3 tools/build_terrain.py --src ../src_data --out data/terrain
```

v4 以降は実測 DEM（§13）を使います。初回は DEM の縮約に約 40 秒、2 回目以降は `--reuse-dem` で縮約結果を再利用でき、全体で約 20 秒です。
同じコマンドで、湖沼・河川による地形の加工（`tools/water.py`）と `data/water.json` の書き出しも行われます（`--no-water` で加工なし、`--elevation procedural` で v3 と同一の手続き生成地形）。北限（37°40′23″）より北の帯は、色を落としながら海へ沈めて「範囲外」と分かるようにしています（`NORTH_LIMIT`, `FADE_END`）。

## 11. 都市・新幹線駅・ランドマーク（v2 追加）

### 11.1 全体像

```text
scene
 ├─ environment
 ├─ terrain      地形タイル（v2: 市街地の地表色を頂点カラーに追加）
 ├─ cities       建物 InstancedMesh（32km タイルごとに 1 つ）       … js/cities.js
 ├─ stations     駅のホーム板 + ピン（InstancedMesh 2 つ）           … js/stations.js
 ├─ landmarks    ランドマーク（1 件 = 1 Mesh = 1 draw call）         … js/landmarks.js
 ├─ actors       （将来）列車・キャラクター
 └─ fx           （将来）演出
```

- 起動時に読むのは `data/cities.json` / `stations.json` / `landmarks.json`（合計約 60KB）だけ。建物とランドマークのジオメトリは**カメラが近づいたときにブラウザ内で生成**します（追加のモデル・テクスチャファイルなし）。
- 既存の地形・カメラ・操作・LOD・座標系（`latLonToWorld()` / 1 unit = 1 km / 縦 3 倍）は変更していません。
  地形側の変更は「市街地色のフック `setUrbanField()`」「詳細標高の先読み API `requestChunkData()`」の追加のみです。
- 海面（`environment.js`）は、2 枚の巨大三角形から**同心円分割の円板**に置き換えました。
  見た目・UV は同じで、地表近くで海面が陸地・建物の上に描かれてしまう深度精度の問題を防ぎます（v1 でも低空で発生していたもの）。

### 11.2 都市メッシュの仕組み

| 見え方 | 表現 | コスト |
|---|---|---|
| 遠景（全体俯瞰〜数百km） | **地形の頂点色を市街地色（明るい灰色）に**。都市の広がりが地図のように見える | draw call・三角形の追加ゼロ |
| 中景（〜320km） | 32km タイルごとの InstancedMesh で、**高い建物から順に一部だけ**描く（超高層の核＝スカイライン） | タイル 1 枚 = draw call 1 |
| 近景（〜14km） | タイル内の全建物（低層の街区まで） | 1 棟 = 10 三角形 |

- **建物 = 底面なしの単位直方体 1 種類**（geometry・material 共有）。幅・奥行き・高さ・向き・色をインスタンスごとに変える。
  頂点カラーで屋上をやや暗く、壁の足元を暗く（簡易 AO）して、近景でも単調になりすぎないようにしています。
- **配置**：全国共通の 0.37km 格子。各セルは「その地点で最も影響の強い都市」が担当（隣接都市の重複生成なし）。
  - 密度 = 都市中心からのガウス減衰 × 値ノイズ（輪郭を不規則に）、または副都心（`cores`）の強さ
  - 核に近いほど 1 セル 2 棟・高層・細身・ガラス色。郊外ほど低層・広い面・コンクリート／ベージュ系
  - 都市ごとに街路の向き（回転）を変える
- **地形との整合**：
  - 標高 2m 未満・セルの四隅のどこかが海（0.5m 未満）→ 建てない（**海上・海岸線際に生成しない**）
  - 斜面 95m/km 超 → 建てない、45〜95m/km → 確率的に間引き＋高さを抑える（**急斜面に大量生成しない**）
  - 底面はセル内の低い側の標高に合わせ、地中へ基礎を 0.12 伸ばす（**浮かない・突き抜けない**）
  - 詳細標高（1km）を読み込んでから生成（`terrain.requestChunkData()`）
  - ランドマーク・駅の周囲（0.25〜0.95km）には建てない
- **生成**：64km チャンク単位でジェネレータ関数として生成し、1 フレームあたり 5ms までに分割（カクつき防止）。生成結果は同じ seed で毎回同じ街並み。

### 11.7 ランドマークの簡略化方針

- **すべて Three.js の基本形状（箱・円柱・円錐台・トーラス・押し出し形状）を組み合わせたオリジナルの簡略モデル**です。外部の 3D モデル・画像・テクスチャは一切使っていません。
- 写実より**遠景でのシルエットと色**を優先（スカイツリーの細さ、東京タワーの赤白、名古屋城の緑青と金鯱、熊本城の黒、金閣の金、鳥居の朱など）。
- 大きさ：塔はおおむね**地形と同じ縦 3 倍 × 1.2〜1.4 程度**（スカイツリー 634m → 高さ 2.3 = 地形換算 約 770m）、小さな建物（金閣・鳥居など）は 6〜30 倍に誇張。
  ただし最大でも富士山（Y≒11）の 1/4 未満で、都市全体より大きくはなりません。
- 大仙陵古墳は建築物ではなく、**地表に張り付いた低い板の重なり**（濠＝水色、墳丘＝濃淡の緑）。水平約 2 倍で MAP VIEW から形が読めます。
- 各モデルは部品を `GeoBuilder`（`js/meshkit.js`）で頂点カラー付き 1 ジオメトリに結合し、共有マテリアル 1 枚で描画（1 件 = draw call 1、三角形 60〜約 4,200）。
- 生成はカメラが表示距離 + 40km 以内に入ってから（その地点の詳細標高を読み込んだ後）。地表の高さが変われば自動で置き直します。

### 11.8 ラベルの距離制御

既存の HTML ラベル方式（重なったら優先度の低い方を隠す）をそのまま拡張しています。

| 距離 | 表示されるもの |
|---|---|
| 広域（〜3400km） | 既存の主要地名＋大都市（metro）＋主要駅（〜700km）＋大型ランドマーク（〜420km） |
| 中距離（〜300km） | 地方中枢・30万人以上の都市・ランドマーク |
| 近距離（〜170km） | その他の都市・全駅（〜150km）・小さなランドマーク（〜120km） |

- 重なり時の優先度：大都市 > 主要駅 > 大型ランドマーク > 地方中枢 > 一般都市 > 一般駅。
  ただし**近距離（駅 70km・ランドマーク 40km 以内）では駅名・ランドマーク名を都市名より優先**。
- 既存 `places.json` に同じ都市のラベルがある場合（東京・大阪など）は二重に作りません。
- ラベル DOM は全部で約 310 個ですが、同時に表示されるのは通常 10〜50 個程度。距離外のものは投影計算も省略し、地表高さの再計算は 20 フレームに 1 回です。

### 11.10 将来の DHT EXPRESS との接続

```js
import { GeoPolyline, attachStationsToRoute } from './js/route.js';

// 1) 東京→鹿児島中央の線路の緯度経度列（将来用意する）からルートを作る
const route = new GeoPolyline(ROUTE_LATLON, { totalKm });

// 2) 駅にルート上の km を付ける（到着イベントの判定用）
const nodes = attachStationsToRoute(route, DHT.stations.list);
//    nodes[i] = { id, name, major, seq, lat, lon, routeKm, offsetKm, ... }

// 3) 進行（DHT 1回 = 1km）ごとに
const p = route.getPointAtKm(progressKm);          // 列車の位置・向き
const arrived = nodes.filter((s) => prevKm < s.routeKm && s.routeKm <= progressKm);
arrived.forEach((s) => s.major ? bigArrivalEvent(s) : smallArrivalEvent(s));

// ランドマーク通過も同様に
const lm = DHT.landmarks.getById('akashi-kaikyo-bridge');
const lmKm = route.locate(lm.lat, lm.lon).km;
```

| 使いたいもの | 参照先 |
|---|---|
| 駅一覧（順番付き） | `DHT.stations.list`（seq 順）、`DHT.stations.getById('hakata')`、`DHT.stations.major` |
| 駅の緯度経度列 | `DHT.stations.latLons()` |
| ランドマーク | `DHT.landmarks.items`、`DHT.landmarks.getById(id)`（`mesh` はモデル） |
| 都市 | `DHT.cities.cities`（id・name・rank・lat・lon・x・z・半径 r） |
| Raycaster | 駅 `mesh.userData.items[instanceId]`、ランドマーク `mesh.userData`（id, name, type, lat, lon）、建物 `DHT.cities.cities[mesh.userData.cityOf[instanceId]]` |
| ルート上の km | `route.locate(lat, lon)` → `{ km, offsetKm }`（`route.js` に追加） |

今回は列車・走行ルート・到着イベント・ポップアップは**実装していません**（データと API だけ用意）。

## 12. 飛空艇操作・湖沼・河川（v3 追加）

### 12.1 EXPLORE VIEW（飛空艇操作）

「FPS の自由カメラ」から「日本列島の上を飛ぶ飛空艇」に作り直しました（`js/controls.js` の `ExploreController`）。**MAP VIEW（`MapController`）は一切変更していません**（左ドラッグ回転・右ドラッグパン・ホイールズーム・プリセット・慣性はそのまま）。

| 考え方 | 実装 |
|---|---|
| Yaw ＝ 進行方向 | `A/D`・`←/→` は機首方位の旋回だけ（ストレイフ廃止）。マウスの左右も同じ Yaw を回す（見ている方向へ飛ぶ） |
| Pitch ＝ 視線だけ | マウスの上下は視線のみ。`W` は Pitch に関係なく**水平**に進むので、地面を見下ろしても突っ込まない |
| 高度 ＝ 独立操作 | `Q` 下降・`E` 上昇（`Space` も上昇） |
| 固定速度 | ホイールでの速度変更は廃止。`Shift` だけで高速化 |
| 慣性なし | 押せば即移動・離せば即停止。旋回だけ 0.07 秒程度のなめらかさ |

定数（`js/controls.js` 冒頭の `AIRSHIP`。1 world unit = 1 km）：

| 定数 | 値 | 内部速度 |
|---|---|---|
| `CRUISE_KMH` 水平（通常） | 30,000 km/h | 30000 / 3600 = **8.333… units/s** |
| `BOOST_KMH` 水平（Shift） | 90,000 km/h | 90000 / 3600 = **25 units/s** |
| `CLIMB_KMH` 垂直（通常） | 10,000 km/h | **2.777… units/s** |
| `CLIMB_BOOST_KMH` 垂直（Shift） | 30,000 km/h | **8.333… units/s** |
| `YAW_DEG_PER_SEC` 旋回 | **72°/s**（90° ≒ 1.25 秒、Shift の影響なし） | 30,000 km/h での旋回半径 約 6.6km |
| `MIN_AGL` 最低高度 | **1.0 km**（1,000m） | 周囲 `PROBE_R` = 0.8km の最も高い地表から測る |
| `LOOKAHEAD` 先読み | 1.5・3・5 km 先 | 山が迫ると最大 14 units/s で前もって上昇 |
| `MOUSE_SENS` | 0.0022 rad/px（v2 と同じ） | X・Y とも符号を反転 |
| `PITCH_LIMIT` | ±1.5 rad（±86°） | カメラが上下反転しない |

- 速度はすべて `deltaTime` 基準（`位置 += 速度 × dt`）なので FPS に依存しません。`main.js` では EXPLORE VIEW だけ dt の上限を 0.25 秒にしてあり、**4fps 以上なら実時間どおり**に進みます（MAP VIEW・カメラ移動は従来どおり 0.1 秒）。
- 旋回角速度 72°/s は、30,000 km/h（8.3 km/s）で飛びながら「急すぎず、しかし本州の向きに沿って曲がる・湾を回り込む」のに 1〜2 秒で済む値として選びました。90,000 km/h でも同じ角速度なので、高速時は大きな弧になります。
- 高度の扱い：HUD の **ALT は「対地高度（world unit = km）」**で、v2 と同じ定義です（地形の縦 3 倍誇張とは独立した、カメラの高さ）。最低高度 1.0 は周囲 0.8km で最も高い地表を基準にしているため、山腹では ALT 表示が 1.0 km より大きくなることがあります。
- 富士山（Y ≒ 11.3）・北アルプスなどの高い山に向かって飛んでも、毎フレーム「最低高度 1km」＋「進行方向の先読み上昇」でカメラが山の内部に入ることはありません（§12.11 で毎フレーム検証）。
- HUD の SPD は水平速度：飛行中は **30,000 km/h**（Shift 中 **90,000 km/h**）、停止中は 0 km/h。垂直速度は表示しません。
- MAP VIEW から切り替えたとき、または低い所で EXPLORE VIEW に入ったときに 1km より低ければ、毎秒 20 units でなめらかに 1km まで上昇します（地表には潜りません）。

### 12.5 地形との干渉対策（`tools/water.py`）

手続き生成の地形に青い板を置くだけだと、丘が湖面を突き抜けたり、川が山を登ったりします。そこで地形データ（`data/terrain/`）を**事前生成の段階で加工**しています（JS の実行時処理は増えません）。

**湖**
1. 湖の範囲と、1km 格子のセルが湖に掛かる範囲（湖岸から 1.45km）の地形を **水面 − 7m の平坦面**にならす（切土・盛土）。
2. その外側は、高低差に応じて 2〜8km かけて元の地形へなめらかに戻す。
3. 粗い地形（4km 間隔）も同様にならす（遠景・全体俯瞰で湖が地形に埋もれない）。
4. → 湖面の下に必ず地形が 7m（Y で 0.021）以上あるので、**Z ファイティングも突き抜けも起きません**（対数深度バッファの精度に対して十分な差）。

**河川**
1. 流路を 0.25km 間隔に細分化（Catmull-Rom で滑らかに）。
2. 各点で「左右 1.2km の断面の最低標高」を取り、**上流から下流への累積最小値**を水面高にする（＝**水面は必ず下流に向かって単調に下がる。山を登らない**）。2km 窓で平滑化した後もう一度単調化。
3. 水面の下限は陸上で 25m、海に注ぐ川は河口 4km で 7m まで下げる（低地を掘り過ぎて、地形色が海岸の砂色の帯にならないように）。下限も下流へ単調なので、水面の単調性は保たれます。
4. 流路沿いの地形を「前後 ±1km の水面の最小値 − 6m」まで掘り下げ、両側は掘った深さに応じて 2〜7km の幅で元の地形へ戻す（谷になる）。水面の下限より低い低地だけは最大 +25m まで盛る（自然堤防程度。海・湖の湖底は埋めない）。
5. 河口は、最後の向きのまま流路を延長して地形が海面に達した所で終わる（河口がわずかに内陸で切れない）。陸の川沿いは海面下にしない（海が入り込まない）。
6. 湖は先に処理した隣の湖（富士五湖どうし、霞ヶ浦と北浦など）の湖底を高くしないよう、加工済みの地形に対して順に適用します。

**検証**（`data/terrain` と `data/water.json` を突き合わせた数値チェック）
- 20 湖すべてで、湖面ポリゴン内（50m 間隔でサンプリング）の地形の最高点が水面より **6.6〜7.4m 低い**（突き抜け 0 件）。
- 26 河川すべてで、リボンの中心と両岸（各区間 12 点）の地形が水面より低い（最も近い所でも 1.2m 下、それ以外は 4.7m 以上下）。
- 26 河川すべてで、水面標高が上流→下流で一度も上がらない（単調減少）。

- 地形が実際の谷筋と一致していない所（例：木曽谷、江の川が中国山地を横切る所、紀の川上流）では、川が深い谷を刻む形になります。**流路は地理的に正しい位置を優先し、地形の方を川に合わせて削る**という妥協点です（最大 700〜1,100m の掘り込み）。
- 加工で変わった頂点は詳細地形全体の約 3.1%。湖・川から離れた地形は v2 と 1m 単位で同一です（`--no-water` で v2 と完全に同じ地形を再生成できることを確認済み）。
- 地形の再生成：`python3 tools/build_terrain.py --src ../src_data --out data/terrain`（§10 の手順に `ne_10m_rivers_lake_centerlines.geojson` を追加）。湖・河川の定義は `tools/water_defs.json`。

### 12.6 データの作り方・出典・ライセンス

| データ | 出典 | ライセンス | 商用利用 | 再配布 | 加工内容 |
|---|---|---|---|---|---|
| 利根川の流路 | Natural Earth `ne_10m_rivers_lake_centerlines`（https://github.com/nvkelso/natural-earth-vector） | **パブリックドメイン** | 可 | 可（条件なし） | 0.25km に細分化・平滑化、水面高と川幅を付与、簡略化 |
| 利根川以外の 25 河川の流路 | **本リポジトリで作成**（下記の方法） | **CC0** として扱えます | 可 | 可 | 同上 |
| 20 湖沼の形状 | **本リポジトリで作成**（下記の方法） | **CC0** として扱えます | 可 | 可 | 三角形分割 |
| 水面標高・地形の加工 | `tools/water.py` による計算結果 | CC0 | 可 | 可 | — |

**作成方法（利根川以外）**
- 一般に公開されている地図（地形図・道路地図など）の知識をもとに、各河川の**源流・主要な通過地点（市町村・合流点・峡谷・河口）**の緯度経度を、本流に沿って 6〜29 点（平均約 12 点）ずつ手で置き、Catmull-Rom 曲線で滑らかにつないでいます。湖も同様に、湖岸の特徴的な地点（入江・半島・流出口）を 4〜29 点で囲んでいます。
- 検証は、Natural Earth の海岸線（パブリックドメイン）と本リポジトリの都市・駅座標（`cities.json`・`stations.json`）に重ねた確認図で行いました（例：天竜川が浜松の東を通る、多摩川が府中・調布の南を通る、荒川が熊谷の南を通る、四万十川が江川崎で南へ曲がる など）。
- 精度はおおむね **0.5〜2km**（ステージの地形 1km 格子と同程度）。GIS レベルの精密さではありません。
- 公的な水系データ（国土数値情報・地理院ベクトルタイル・OpenStreetMap 等）は、作業環境からダウンロードできなかったこと、また **ライセンス表記・継承義務を増やさない**ために使っていません。OpenStreetMap 由来のデータ（ODbL）は一切含みません。
- 将来、国土数値情報（河川 W05・湖沼 W09 など）へ差し替える場合は、`tools/water_defs.json` の `line` / `rings` を置き換えて `build_terrain.py` を再実行するだけです（出典表記の追加を忘れずに）。

### 12.7 都市メッシュとの水域マスク

- `cities.js` の建物配置ループに **水域判定 `waterMask(x, z, 0.22)`** を追加しました（`water.isWater()` を `cities.setWaterMask()` で登録）。
- 判定する場所は、既存の「海（標高 2m 未満・四隅が 0.5m 未満）」「急斜面」「駅・ランドマーク周辺」と同じ並び。**湖面・川面の上と、水際から 0.22km 以内のセル**（格子 0.37km の半分＋余裕）には建物を作りません。
- 判定は 8km バケットの空間ハッシュ（湖は外接矩形 → 多角形内外・岸までの距離、川は線分までの距離 − 川幅/2）。1 チャンク生成あたりの増加時間はわずかで、既存の 5ms/フレームの生成予算に収まっています。
- 駅・ランドマークの位置は変更していません。湖・川のための地形の加工は駅・ランドマークから離れており、表示位置は従来どおり地表の高さから自動で決まります。

## 13. 実測 DEM による地形（v4）

### 13.1 目的と結果

v3 までの標高は「主要な山脈・火山・平野の位置と概略標高をパラメータで置き、ノイズで補う」手続き生成でした。大きな山脈は表現できていましたが、**御坂山地・房総丘陵・三浦丘陵・丹沢の尾根・鈴鹿・六甲などの地域スケールの山地・尾根・盆地の情報がそもそも存在しない**ことが問題でした（高さ倍率の問題ではない）。

v4 では陸地の標高を **実測 DEM（Copernicus DEM GLO-90）** に置き換えました。**垂直倍率は v3 と同じ 3 倍のまま**、高さの誇張は一切増やしていません。

- **御坂山地**：甲府盆地（約 280m）と河口湖（湖面 831m）の間に、1km 格子で 1,480〜1,640m の山地帯が連続して再現され、甲府側の低空からは富士五湖が見えなくなります（v3 では甲府盆地の縁から富士五湖まで平坦な緑地が続き、湖が丸見えでした）。
- **房総半島南部・三浦半島南部**：清澄山・鋸山・愛宕山周辺の数百 m の丘陵、三浦丘陵（大楠山など）の起伏が実データどおりに出ます。北側の平野（下総台地・横浜〜川崎の低地）との差も実データ由来です。
- 丹沢・箱根・伊豆・八ヶ岳・南／中央／北アルプス・鈴鹿・紀伊・六甲・中国・四国・九州山地も、平野・盆地との境界が実際の位置に出ます。
- 配信データ量・ファイル数・LOD 構造・draw call・三角形数は **v3 とほぼ同じ**です（§13.7）。

### 13.2 使用 DEM の選定

| 候補 | 判断 |
|---|---|
| **Copernicus DEM GLO-90**（採用） | 日本全域を 90m でカバー。実測（TanDEM-X）ベース。**全世界向けに無償公開、加工・再配布可、帰属表示のみ必要**（ライセンス本文を確認）。1°タイルの COG で、必要範囲だけを取得できる。 |
| 国土地理院 標高タイル / 基盤地図情報 DEM | 精度は最良（5m / 10m）。ただし基盤地図情報の大量複製・公開には測量法の承認手続きが関わる場合があり、本リポジトリの「事前生成した派生データを GitHub Pages で再配布する」形では条件の確認が重くなるため今回は不採用。1km 格子への縮約では 90m との差はほぼ出ない。 |
| SRTM（NASA, 3 秒角） | パブリックドメインで再配布も自由。ただし Copernicus より古く（2000 年）、急峻な山地に欠損（void）が残る。 |

データの出典・ライセンス・クレジット表記は [§4.4](#44-標高v4copernicus-dem-glo-90) にまとめています。**DSM（建物・樹木を含む表面高）** なので、都市部は数 m〜十数 m 高めに出ますが、1km 格子・3 倍強調の広域ステージでは影響は小さく、超高層ビル・鉄塔などの細い突起は下記のオープニングで除いています。

### 13.3 処理の流れ（`tools/build_terrain.py` + `tools/dem/`）

```text
Copernicus DEM GLO-90（1°タイル 88 枚、約 150MB、開発機のキャッシュにだけ保存）
  ↓ tools/dem/copernicus.py      … Natural Earth の陸地に掛かるタイルだけ取得（海だけのタイルは存在しない）
  ↓ tools/dem/resample.py        … 64km チャンクごとに
  │   1) 3×3 画素（約 270m × 225m）のグレースケール・オープニング … DSM のビル・鉄塔など細い突起を除去
  │   2) ワールド座標（正弦図法）0.125km 間隔へ双線形で再標本化
  │   3) 1km 頂点ごとに「頂点を中心とする 1km 四方」の 64 サンプルから mean / p90 などを計算
  │   4) 尾根保存ブレンド  h = mean + 0.5 × (p90 − mean)
  ↓ build_terrain.py
  │   ・海岸線は Natural Earth のまま（陸／海の判定は v3 と同一）。陸側 0.6km で DEM 標高へなじませる
  │   ・陸の下限：海岸線上 2m → 内陸 1.5km 以上で 10m（海抜 0m 以下の干拓地なども 10m に。海面 Y=0 の板が透けない）
  │   ・海底は DEM に無いので v3 と同じ「海岸からの距離」による簡易水深（実測ではない）
  │   ・北限より北の帯は v3 と同じく海へ沈める
  │   ・ランドマーク（橋以外）の足元 0.6km を実際の地盤高にそろえる（下記 13.6）
  │   ・湖沼・河川の加工（tools/water.py、13.5）
  ↓
data/terrain/coarse.bin（4km）・hi/h_X_Z.bin（1km × 214 チャンク）・manifest.json（形式は v3 と同一）
```

- 4km の粗データは v3 では 1km データの単純な間引きでしたが、それだと 4km 未満の山地・尾根が遠景で消えるので、**1km 格子上の 5×5 で同じ尾根保存ブレンド**を取っています（海岸の頂点は間引き値を使い、海岸線は動かさない）。
- DEM が欠けた陸地（タイルが無い所）は v3 の手続き生成で補完する仕組みを残していますが、**今回の生成では補完 0 頂点**（陸地 252,183 頂点すべて DEM）。下限 10m を適用した低地の頂点は 13,994（5.5%）。
- `manifest.json` の `elevation` に DEM 名・帰属表示・縮約方法・頂点数を記録しています。

- 全河川で水面標高は上流→下流で単調減少（水が山を登らない）。`data/water.json` の河川 `points` は補正後の流路・水面・川幅です。`tools/water_defs.json`（手描きのソース）は変更していません（補正は生成時に毎回再計算）。
- 湖沼・河川の加工で変わった頂点は陸地の 3.4%（v3 は 3.1%）。

### 13.6 都市・駅・ランドマーク・橋

- 都市の建物・駅・ランドマークは v3 から **地表の高さを実行時に `terrain.getSurfaceY()` で取って置く** 実装なので、旧地形の高さに固定されているものはありません（コードの変更なし）。
- **ランドマークの足元**：1km の尾根保存ブレンドは周囲の山の高さを拾うため、海辺の厳島神社が山腹（80m）に乗る・金閣寺／姫路城／熊本城が背後の山の高さに引っ張られるなどの問題がありました。`build_terrain.py` で、橋以外の 14 件の足元 0.6km の頂点を **実際の地盤高（DEM の半径 300m の下位 20% 値＝DSM の樹木・建物を避けた値）** にそろえ、外側 0.7km で元の地形へ戻しています（例：厳島神社 392m → 3m、金閣寺 → 96m、熊本城 → 24m）。
- 検証（実ブラウザ、各ランドマークを近景で撮影：`qa/v4/landmarks/`）：17 件すべて構築され、**浮き 0 件**（モデルの底＝周囲 5 点の最も低い地表）、中心の地表への埋まり 0〜2m（斜面のため。従来と同じ設計）。駅 46 件は全件、地表の高さに一致（差 0）。
- 都市の建物 **45,773 棟**（東京・横浜・横須賀・名古屋・大阪・京都・広島・福岡・甲府・静岡・館山・熊本を巡回して生成）を検査：**水上 0 棟、基礎が地表から浮いた建物 0 棟**、屋上が地表より下 9 棟（v3 の同じ検査では 1 棟。急斜面の小さな建物で、基礎は地中に伸びているため画面上は埋まって見えない） 棟。急斜面・海岸・水域・駅／ランドマーク周辺の除外ロジックは v3 のまま有効です。
- 橋（明石海峡大橋・瀬戸大橋・関門橋）は海上の構造物で、橋脚・主塔は地表（海面）から、両端は陸の地表から立ち上がる既存の実装のまま、新地形で不自然な浮き・埋まりがないことを画像で確認（`cmp_17`〜`cmp_19`）。淡路島北部・塩飽諸島・関門の両岸の起伏が実データになりました。

### 13.8 500m など、さらに細かい LOD について（今回は追加しない）

- まず v3 と同じ 1km / 4km 構造に実 DEM を入れて検証した結果、**御坂山地・房総丘陵・三浦丘陵・丹沢・箱根・六甲は 1km 格子で十分に地形として認識でき**（13.1 の比較画像・13.10 の数値）、今回の目的は 1km で達成できたため、500m LOD は追加していません。
- 1km で不足が残るのは、幅 1km 未満の峡谷（大井川・天竜川・木曽谷など）と、尾根の最高点の高さ（尾根保存でも 90m 原データの最高点より 100〜200m 低い）です。EXPLORE VIEW の最低高度 1,000m（Y で 1 unit ≒ 実標高 333m の 3 倍強調）から見る限り、主な違和感はありません。
- 追加する場合の見積もり：同じ 64km チャンクで 0.5km 格子（131×131）なら 1 枚 約 34KB、全 214 枚で約 7.3MB（1km の約 3.8 倍）。カメラから 40〜60km 以内だけを 500m にする 3 段目の LOD として、`tools/dem/resample.py` の `SUB`（1km あたりの細格子数）を変えたもう 1 系統の出力を作り、`terrain.js` の詳細タイルを 4 分割する形が素直です（13.11）。250m は 1 枚 約 130KB・全体 約 28MB になり、GitHub Pages では範囲を絞らない限り推奨しません。

### 13.9 再生成手順

```bash
pip install numpy scipy pillow tifffile imagecodecs scikit-image
mkdir -p ../src_data && cd ../src_data
B=https://raw.githubusercontent.com/nvkelso/natural-earth-vector/master/geojson
for f in ne_10m_land ne_10m_minor_islands ne_10m_lakes ne_10m_rivers_lake_centerlines; do curl -LO $B/$f.geojson; done
cd ../dht-express-stage
python3 tools/dem/copernicus.py --src ../src_data          # Copernicus DEM GLO-90 を ../src_data/dem/cop90/ へ（88 タイル・約 150MB・初回のみ）
python3 tools/build_terrain.py --src ../src_data --out data/terrain   # 約 1 分（2 回目以降は --reuse-dem で約 20 秒）
# 任意：検証
python3 tools/dem/compare_methods.py --src ../src_data --out qa/v4/dem_methods.md --png qa/v4/dem_profiles.png
python3 tools/dem/river_overlay.py   --src ../src_data --water data/water.json --out qa/v4/rivers_overlay.png
```

| オプション | 内容 |
|---|---|
| `--elevation procedural` | v3 の手続き生成地形（比較用。v3 の `data/terrain` と 1 バイト単位で同一になることを確認済み） |

| 環境変数 `DHT_SNAP_KM` / `DHT_RIVER_CORE` | 河川の谷筋補正の回廊の半幅（既定 7km）／河床へ下げる範囲（既定 0.55km） |

### 13.11 将来さらに高解像度化する場合

- **DEM の差し替え**：`tools/dem/copernicus.py` の `DemMosaic` と同じインターフェース（`window(lat0, lat1, lon0, lon1)` → 配列と緯度経度の原点・画素間隔）を持つクラスを作れば、GLO-30・国土地理院 DEM（10m/5m、GeoTIFF 化したもの）などに差し替えられます。縮約・水系・出力は共通です。ライセンスと帰属表示を §4.4 と `manifest.json` に追記してください。
- **500m の 3 段目 LOD**：`resample.py` の `SUB` を 16 にして 0.5km 格子の統計を作り、`hi2/` などの別ディレクトリに 64km × 131² のチャンクとして出力、`terrain.js` で詳細タイルをさらに 4 分割する（スカートと双線形補間の `getHeightMeters` に 3 段目の参照を追加）。範囲を本州中部などに限れば数 MB で済みます。
- **海底**：GEBCO 等の水深データを同じ方法で縮約すれば、海底も実測にできます（現在は簡易水深）。
- **湖岸線・川**：国土数値情報（湖沼・河川）などに差し替える場合は `tools/water_defs.json` を置き換えて再生成（谷筋補正・湖面標高の算出はそのまま使える）。
